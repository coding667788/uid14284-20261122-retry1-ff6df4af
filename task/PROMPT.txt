给企业账号做一个可离线演练的恢复控制器。原认证器丢失后，恢复依据来自不同保管域的合成证明。账号经历身份世代切换，每个受托人有明确的组织、保管域和有效期。服务高风险，需从预先批准的配方中满足任意一份。配方同时指定各证明类型的数量和哪些证明必须分属不同组织或保管域。同一证明只能被选一次，证明粘在账号、恢复申请、身份世代、配方版本及所选新认证器摘要上。签发、撤销及变更都以逻辑时刻和事件序号排序，测试夹具中不存真实密钥。

一个申请先 reserve 选取最少的新证明，再按升序 ID 列表决胜。证明随后进入冻结窗口，旧认证器和预先登记的安全联系人分别有权提出异议。冻结开始后只能用原配方与当前仍有效的同一组证明完成，失效后必须生成新的预留和完整的冻结窗口。旧认证器发起的异议若发生在有效世代且其时刻恰在冻结截止点，同一批按异议优先处理；其余并发事件按输入指定序号。一个已取消申请留下永久终止回执，所有曾预留证明自冻结起只可由该次预留使用，即使取消或未激活也不可转用于后续预留。账号可并行接收多个申请，但每个身份世代只能成功推进一次，成功后同世代其余申请原子取消，旧认证器与本次未选中的认证器均不得变成新世代的有效凭证。activate 在同一 SQLite 事务复核异议、当前世代、申请绑定、截止及撤销，提交新身份世代、证明消费和稳定回执。相同请求 ID 和内容的重放只读原回执，异内容的同 ID 整批失败。

新增 simulate_loss。对尚未申请恢复的账号，输入未来可签发到同一恢复申请和新认证器的合成证明目录，只输出在无故障和任意一个保管域失效情形下均能选到有效配方的最小准备清单。每种情形可以选不同配方，准备清单需预先固定。按费用、准备条数和 ID 列表决胜；无解返回第一个连全部候选也不可恢复的失效情形和缺失要求。支持 26 条候选与 8 个保管域，说明如何重用各情形的配方可行性。至少覆盖同组织跨保管域但不独立、最低成本配方失效而备用配方可用、准备清单会选用两种配方共同需要的证明、两个恢复申请并发争用、同截止异议、进程提交前退出及提交后响应丢失。用独立小模型回放逻辑事件与清单最优解。

从空仓库实现，目标为 Windows 原生 Python 3.12、标准库、CPU。以 python -m solution <命令> CASE.json 运行，状态类命令接收 --db DB.sqlite。stdout 输出可重现的 UTF-8 JSON，输入结构错误含错误码和字段位置。随项目交付可直接运行的虚构样例、定义完整接口和复现步骤的 README，以及 python -m unittest discover -s tests -v 可执行的断言测试。
